# OpenMeido 记忆系统白皮书与架构指南

最后更新：v0.0.30 (2026-05-22)

欢迎阅读 OpenMeido 记忆系统指南！

OpenMeido 的记忆系统并非单一的存储结构，而是一个**分层级、高自适应、具有长短期记忆与情感价值的多元复合记忆引擎**。它由多个协同工作的子系统组成，以实现秒级会话、中性待办管理、即时工作跟进、年级用户画像以及长期情感沉淀。

---

## 1. 记忆系统的分层架构

为了在确保对话流畅度的同时，保持对长期稳定事实的敏感度，记忆引擎被划分为以下几个主要层级：

| 层级 | 系统组件 | 中文释义 | 主要职责 | 物理存储与媒介 | 时间尺度 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **L1** | **Episodes (SQL)** | **短期对话流** | 记忆“刚才聊了什么”，完整重放上下文。 | `episodes` 表，保存所有 speaker 类型（含工具行）。 | 秒级到天级 |
| **L2** | **Episodes (Vec0)** | **关联语义记忆** | 检索“过去什么时候聊过类似话题”，跨时空联想。 | `episodes_vec` 向量虚表 (BGE ONNX 512维)。 | 周级到月级 |
| **L3** | **Facts (Personal)** | **长期稳定画像** | 记忆“用户是谁、宠物、喜好、名字等”，塑造人物对用户的理解。 | `facts` 表 (`category='personal'`)，支持 Supersession 与 Scope 隔离。 | 永久有效 |
| **L3** | **Facts (Work)** | **短期工作事实** | *已在 v0.0.30 废弃* | *已废弃与移除 (Option B)，相关信息流直接并入平行 Raw Episodes 与动态 Tool Calling 中。* | - |
| **L4** | **Affinity** | **情感好感度** | 累积“两人亲密度、互动深度”，驱动动态性格语调。 | `persona_affinity` 表，经过 median 滤波与每日 capped 保护。 | 永久累积 |

## 2. 整体数据流与运行时架构

在每一次用户与 AI 交互的过程中，记忆系统都在后台静默运转，组装上下文、存储交互并按需触发反射。

```
                            ┌─────────────────┐
     用户发送消息 ──────────▶ │   chat.ts 主循环  │ ◀─────── 获取当前 active 角色 (不缓存)
                            └────────┬────────┘
                                     │
                                     ▼
                           MemoryService.retrieve()
                                     │
                 ┌───────────────────┴───────────────────┐
                 ▼                                       ▼
          L1: 最近 N 条 Episode                    L2: 向量 KNN 回忆
          (通过 ts 顺序拉取)                     (输入嵌入匹配 512d)
                 │                                       │
                 └───────────────────┬───────────────────┘
                                     ▼
                          MemoryService.factsBlock()
                                     │
                           ┌─────────┴─────────┐
                           ▼                   ▼
                     L3: 个人长期记忆        工作上下文
                   [关于用户的已知事实]     *(由平行 Raw Episodes*
                           │                *和动态 Tool 渲染呈现)*
                           └─────────┬─────────┘
                                     ▼
                              注入 System Prompt
                                     │
                                     ▼
                          LLM 生成回复 & 运行工具
                                     │
                 ┌───────────────────┴───────────────────┐
                 ▼                                       ▼
          新 Episode 入库                       自动触发 L3 异步反射整理
        (user/assistant/tool)               (每 5 次纯聊天个人回合触发)
```

## 3. 双轨 Facts 演进与平行上下文 (v0.0.30 Option B)

过去，我们采用个人（Personal）与工作（Work）的双轨反射机制，分别向 SQLite 中整理两种 L3 事实。

但在实际体验中，**工作上下文（如任务清单、邮件主题、工单状态）属于高度易变、波动频繁的“临时工作状态”**。使用昂贵且慢速的 LLM Reflection 将其持久化到 L3 事实表中，带来了以下几个严重的架构痛点：
1. **记忆陈旧与过期**：反射过程是异步且有计数的，导致写入 Facts 表的信息往往滞后于最新的任务状态，造成记忆“僵死”。
2. **提示词膨胀与注意力稀释**：大量的 project 编号和陈旧工单摘要堆积在 System Prompt 中，严重占据了宝贵的 token 空间，并稀释了模型在日常对话中的情感表现力。

### 解决方案：Option B 并行轨道设计
在 `v0.0.30` 中，我们决定全面废弃 **L3 工作事实抽取**，仅保留 **L3 稳定的个人日常记忆**，工作上下文则采用更为优雅的**平行对话流 + 动态工具召回**进行重构：
- **感情线与工作线平行**：日常感情和对话事实依赖 L3 Facts（稳定且永久有效），工作任务和上下文直接在 L1 历史滑动窗口及 L2 语义回忆中流动，并通过实时 tool 反馈进行即时渲染。
- **反射层纯净化**：`reflectProductivityOnce()` 被关闭退化为安全 stub。反射计数器只对 `'personal'` 纯日常对话进行累加，不再受到任何工具调用回合的干扰。

## 4. 细粒度 Turn 划分与好感度防刷 (Farming)

为了确保好感度（Affinity）的沉淀是真实的情感互动，而不是因为频繁安排任务、查看邮件等工作指令导致“刷分”，我们设计了基于工具行为的细粒度回合分类器 `classifyTurnType`：

1. **`'personal'` (纯日常)**：未调用任何工具的回合。累加个人反射计数器，**应用 Affinity 好感度提升**，界面上为干净的气泡。
2. **`'work'` (工作任务)**：调用了读取文件 `readFile`、收发邮件 `readEmail` / `draftEmailReply`、网页搜索 `google_search` 等工具的回合。**跳过 Affinity 增加**以防止 farming，**跳过反射计数**，同时在 UI 气泡旁显示 `💼` 书包图标以向用户明示工作边界。
3. **`'neutral'` (中性管理)**：调用了待办列表 `addTask` / `listTasks` / `markTaskDone`、剪贴板读取 `readClipboard` 等工具。这属于中性的日常助手性质。**跳过 Affinity 增加**并**跳过反射计数**，但在 UI 界面中**隐藏 💼 图标**，保持界面的亲和力与整洁。

## 5. 跨角色隔离与共享 (Scope)

系统引入了 **Scope** 机制，完美解决了“不同伴侣角色之间记忆如何分布”的痛点：

1. **Shared (共享记忆)**：关于用户自身的属性（如：真实姓名、养的猫名字、所做项目）属于**人本身**。新提取的事实默认标记为 `shared`，当用户切换伴侣（如从女仆切到大小姐）时，这些事实依然能够被感知。
2. **Persona (角色专属)**：人物专有的昵称（如：女仆称呼用户为“主人”、角色特定的内部玩笑）标记为 `persona`，其他伴侣无法越界读取，确保极佳的情感体验隔离。
3. **数据安全与清空**：
   - 删减某个角色时，系统只会清除标记为 `scope = 'persona'` 的专有记忆，**保留用户的 `shared` 属性**。
   - 当用户在 UI 中彻底点击“清空记忆”时，彻底清除 `shared` 和当前角色专属的所有记忆。

## 6. 系统级否定与撤回机制 (Negation & Retraction)

人类会做出更正、否定与撤回。面对“别叫我小李了，我叫小刘”或者“我其实没有养猫”等表述，OpenMeido 设计了**系统级否定与撤回流水线**：

### 1. 反射提取 (Reflection Prompts)
在 L3 反射的 `PERSONAL_PROMPT_HEADER` 中，写入了精确的否定提取指令：
> 如果用户在对话中明确否定、撤回、纠正或驳回了某个已知事实（例如：用户说“我没有猫”、“别叫我小李了”），你必须将该事实的 key 提取出来，并将其 value 设置为 "DELETE"（全大写），confidence 设为 1.0。

### 2. 数据库级自动清理 (SQLite Adapter Purger)
在 SQLite 适配器的 `upsertFact` 逻辑中拦截 `"DELETE"` 操作：
* 当新事实 `value === 'DELETE'` 时，Adapter **拒绝执行插入**。
* 相反，它在事务内发起删除命令：`DELETE FROM facts WHERE key = ? AND category = ? AND (persona_id = ? OR scope = 'shared')`。
* 这一删除操作会**永久并完全清空**该 key 在该角色视野下的整条 supersession 关系链，从而确保它在检索中彻底消失。
* 支持“先删后写”，即在同一反射回合中，先执行旧键删除，再写入新事实（如将 `user.profile.name` 的旧值彻底洗去，并精准写入新值 `小刘`）。

## 7. 开发与扩展指引

如果未来需要为 OpenMeido 记忆系统扩展新的轨道（例如：健康追踪健康记忆轨道 `health`）：

1. **加类型**：在 `types.ts` 中的 `FactCategory` 新增 `'health'` 分支。
2. **写 Prompt**：在 `reflection.ts` 中定义 `HEALTH_PROMPT_HEADER` 和对应 kind。
3. **加服务接口**：在 `service.ts` 中添加 `reflectHealthOnce()`。
4. **定调度**：在 `chat.ts` 的 `maybeTriggerReflection` 中依据特定逻辑（例如检测到 `turnType` 为特定辅助功能）触发此反射。
5. **合入提示词**：在 `factsBlock` 中拼接 `[用户健康指标记忆]` 段。

这套记忆引擎在设计上最大化地将抽取逻辑转化为**模型 Prompt 驱动**，这种弹性结构使得系统具有无限的扩展深度，在任何平台上运行都足够轻量与优雅。
